# 2. Where does Obsidian fit?

This is the important conceptual distinction.

**Obsidian isn't really a competitor to LLM Wiki.**

I'd use it as the **human interface to the compiled Wiki**.

`nashsu/llm_wiki` actually makes this especially natural because its project includes an automatically generated `.obsidian/` directory. citeturn1search0

So:

```text
                 ┌───────────────┐
                 │    Sources    │
                 └───────┬───────┘
                         │
                         ▼
                ┌────────────────┐
                │   LLM Wiki     │
                │                │
                │ compiler       │
                │ maintainer     │
                │ graph          │
                │ retrieval      │
                └───────┬────────┘
                        │
                  Markdown files
                        │
              ┌─────────┴─────────┐
              ▼                   ▼
          Obsidian              Agents
        human browsing       Hermes/Cursor/etc.
```

That's much cleaner conceptually.

### Obsidian's job

You:

- browse the wiki;
- manually inspect pages;
- follow backlinks;
- make occasional corrections;
- visualize relationships;
- add your own notes.

### LLM Wiki's job

AI:

- reads new sources;
- identifies concepts/entities;
- creates pages;
- updates existing pages;
- cross-links them;
- synthesizes across sources;
- preserves provenance;
- finds inconsistencies;
- maintains the structure.

That means **yes, I would integrate the LLM Wiki with Obsidian**.

But I wouldn't make Obsidian responsible for the core intelligence.

Notion occupies approximately the **same architectural layer as Obsidian**, but I think it's a poorer fit for this particular architecture.

Think:

```text
             Human knowledge UI

    Obsidian       Notion       VS Code
       │             │             │
       └─────────────┴─────────────┘
                     │
```

The advantage of Obsidian is particularly strong here because:

**Obsidian vault = ordinary files.**

Your AI-generated wiki remains something like:

```text
wiki/
    ai/
        rag.md
        agents.md
        context-engineering.md

    career/
        skills.md
        projects.md

    people/
        andrej-karpathy.md
```

You can stop using Obsidian tomorrow and nothing meaningful disappears.

That is exactly the **local-first / durable Markdown** philosophy behind these LLM Wiki projects.

So for your system I would choose:

**Obsidian > Notion**

for the canonical human-facing Wiki.

Notion can still be an **input source**.

# 4. NotebookLM is in a completely different place

This is where your question is particularly important.

I would **not integrate NotebookLM into the core architecture**.

NotebookLM is principally:

```text
sources
   ↓
retrieve relevant evidence
   ↓
LLM reasoning
   ↓
answer / artifact
```

A Karpathy-style LLM Wiki is:

```text
sources
   ↓
understand
   ↓
extract
   ↓
reconcile
   ↓
synthesize
   ↓
WRITE / UPDATE persistent knowledge
   ↓
wiki
   ↓
wiki
   ↓
wiki
```

That persistent intermediate artifact is the crucial distinction.

One literal Karpathy-style implementation explains the difference nicely: conventional RAG systems rediscover the corpus when answering, whereas the Wiki continuously accumulates an inspectable body of knowledge. citeturn3search7

So I would position them like this:

| Product | Architectural role |
|---|---|
| **LLM Wiki** | **Knowledge compiler + persistent knowledge layer** |
| **Obsidian** | **Human Wiki UI/editor** |
| Notion | Optional collaborative content source/UI |
| NotebookLM | Ad-hoc source-grounded research environment |
| Hermes | Agent/action/orchestration layer |
| Cursor | Development + agent interface |
| frontier LLM | Reasoning engine |

NotebookLM therefore doesn't need to sit in your primary pipeline.

# 2. Yes: LLM Wiki already implements most of the heavy maintenance loop

The original Karpathy design says the Wiki layer is **owned by the LLM**: it creates pages, updates pages when sources arrive, maintains cross-references, and attempts to keep the knowledge internally consistent. Raw sources remain immutable. citeturn0search2

`nashsu/llm_wiki` goes substantially beyond that conceptual design.

### New artifact arrives

Suppose tomorrow you add:

```text
raw/sources/ai/
    new-agent-paper.pdf
```

Current LLM Wiki can auto-watch `raw/sources/`, detect additions/edits/deletions and put changed sources into a persistent ingest queue. It SHA-256 hashes sources so unchanged files don't need to be reprocessed. citeturn0search0turn0search1

Then its ingest pipeline essentially does:

```text
new-agent-paper.pdf
        │
        ▼
  Parse document
        │
        ▼
 STEP 1 — ANALYSIS
        │
        ├── entities
        ├── concepts
        ├── arguments
        ├── relationships
        ├── contradictions
        └── relationship to existing Wiki
        │
        ▼
 STEP 2 — GENERATION
        │
        ├── source summary
        ├── update entity pages
        ├── update concept pages
        ├── cross references
        ├── provenance
        ├── index/log
        └── human-review items
```

That's not theoretical—the current implementation explicitly separates analysis from generation this way. citeturn0search1

So one source can modify **many existing Wiki pages** rather than merely creating a summary of itself.

That's exactly the behavior we want.


```text

     ↓
```

Nothing else changes.

When you ask something later, retrieval hopefully finds it.

### LLM Wiki instead attempts this

```text
2026-new-multi-agent-study.pdf
                  │
                  ▼
              ANALYSIS
                  │
       ┌──────────┼──────────┐
       ▼          ▼          ▼
    claims    concepts   relationships
       │          │          │
```

That is the core reason I'm now much more comfortable using this project as the central compiler.

# 5. And there is a human-in-the-loop mechanism

This is another thing we were going to have to design ourselves.

Suppose the Wiki currently says:

```text
## Multi-agent architecture

Multi-agent orchestration generally provides...
```

Then Source A claims X.

New Source B strongly claims ¬X.

We don't necessarily want:

```text
LLM decides B is correct
→ silently overwrites X
```

LLM Wiki has an asynchronous **Review system** specifically for matters requiring human judgment. citeturn0search0

So conceptually:

```text
          New evidence
               │
               ▼
       Knowledge Compiler
               │
        ┌──────┴──────┐
        │             │
   confident       uncertain/
    update         conflicting
        │             │
        ▼             ▼
      Wiki          Review
                       │
                       ▼
                     YOU
                       │
              ┌────────┴───────┐
              ▼                ▼
            accept           reject/
                            investigate
```

And crucially, those unresolved review items are exposed through the API/MCP, not trapped in the desktop UI. Hermes could retrieve them. citeturn0search0turn0search3

That gives us a potentially excellent future workflow:

```text
Hermes:
"You have 7 unresolved knowledge issues.

3 are source conflicts.

```

That's very close to our earlier **Wiki Auditor** idea.

```text
Wiki → Markdown → Obsidian → MCP → Hermes
```

Rather:

```text
                         ┌──► Obsidian
                         │
LLM Wiki / Markdown ─────┼──► LLM Wiki UI
                         │
                         └──► LLM Wiki API
                                  │
                                 MCP
                                  │
                               Hermes
```

Obsidian and Hermes are **two different views/consumers** of the same knowledge system.

This is architecturally cleaner.

The current MCP interface exposes things including:

```text
projects
files
read_file
reviews
search
chat
graph
rescan_sources
```

and importantly it calls the application's own API rather than independently crawling the filesystem. Thus Hermes sees the same search, graph and source-watch semantics as the desktop app. citeturn0search3

---

# 7. But I would NOT say the maintenance problem is completely solved

There are three gaps I'd be careful about.

## Gap A — getting everything into `raw/sources`

LLM Wiki is good once something reaches its source system.

But your Second Brain has much broader ambitions:

```text
Google Drive
Gmail [llml]
WhatsApp → self
Telegram
browser bookmarks
GitHub
local directories
web pages
PDFs
DOCX
Excel
...
```

LLM Wiki isn't yet the universal connector/orchestration layer for all of those.

So **this remains our engineering problem**.

I'd solve it with a relatively thin ingestion/capture layer:

```text
Gmail ─────────┐
Drive ─────────┤
WhatsApp ──────┤
Telegram ──────┤
GitHub ────────┤──► Capture/Sync ──► raw/sources/
Bookmarks ─────┤
Local folders ─┤
URLs ──────────┘
```

Once they land there:

> **stop.**

Don't build another knowledge-processing pipeline.

Let LLM Wiki take over.

---

## Gap B — deletion and synchronization are not yet bulletproof

This matters for something you're planning to trust for years.

The current auto-watch does work for changes inside its watched source directory, and a recent independent issue report verified auto-watch, SHA-256 incremental caching, cascade deletion, hybrid search, graph and persistent ingest queue. citeturn0search5

But there are edge cases.

For example, users have reported stale mirrored files and orphaned Wiki pages when an **original external source directory** changes or exclusion rules change. citeturn0search6

So I would *not* design:

```text
~/GoogleDrive
       ↓ direct magical sync
LLM Wiki
```

and assume lifecycle management is solved.

Instead I'd establish a controlled **ingestion boundary**.

# 9. Gap C — global maintenance still needs periodic auditing

The original LLM Wiki design explicitly defines a separate **Lint** operation.

It recommends periodically checking for:

- contradictions;
- stale claims superseded by newer evidence;
- orphan pages;
- missing concepts;
- missing cross-references;
- knowledge gaps;
- things worth researching. citeturn0search2

That's important because incremental ingest has a fundamental limitation.

Suppose source #8 changes:

```text
A → B → C
```

The compiler knows what #8 touches.

But after **10,000 artifacts**, there are second- and third-order relationships that a single ingest pass may never revisit.

So we need two maintenance modes:

```text
              KNOWLEDGE MAINTENANCE

       FAST PATH                 SLOW PATH
           │                         │
    every new artifact          periodic audit
           │                         │
           ▼                         ▼
    incremental ingest           global lint
           │                         │
    affected pages only      inspect whole Wiki
           │                         │
           └──────────┬──────────────┘
                      ▼
                 healthy Wiki
```

This is exactly analogous to incremental compilation + periodic integrity checking.

# 10. Hermes becomes useful again here

I wouldn't have Hermes perform ordinary compilation.

I'd give Hermes **meta-maintenance responsibilities**.

For example:

```text
Hermes Second-Brain Supervisor
│
├── check capture connectors
│
├── ensure new sources arrived
│
├── ask LLM Wiki to rescan
│
├── inspect failed ingestion
│
├── inspect unresolved Reviews
│
├── trigger periodic Lint
│
├── investigate knowledge gaps
│
├── acquire missing sources
│
└── perform external actions
```

That's much more compelling than having Hermes rewrite Markdown itself.

Think:

> **LLM Wiki = compiler**
>
> **Hermes = operating system / orchestrator**
>
> **Obsidian = IDE/browser for your brain**
>
> **Markdown = durable compiled knowledge format**
>
> **MCP = machine interface**

# 11. There's one implementation detail I would watch carefully

The repo is moving fast enough that README promises and implementation can occasionally diverge.

For example, a September 2026 issue found that `overview.md` wasn't actually being regenerated as documented, despite the feature description saying it was. That same tester nevertheless verified most of the other important machinery. citeturn0search5

There have also been scalability concerns around repeatedly rewriting large aggregate pages as Wikis grow; that prompted work to avoid ever-growing aggregate rewrites. citeturn0search8

So I regard `nashsu/llm_wiki` as:

**very promising and unusually close to what we need, but not yet something I'd treat as an infallible knowledge database.**

That's okay because its canonical artifacts are Markdown + raw source files rather than an opaque proprietary store.

### But don't normalize everything into Markdown

This is another important correction.

If LLM Wiki already understands a format natively—PDF, DOCX, EPUB, images, etc.—I'd generally give it the **original artifact**:

```text
report.pdf
     │
     ├──────────────► raw/sources/report.pdf
     │
     ▼
 LLM Wiki parser
```

rather than:

```text
report.pdf
     ↓
Hermes
     ↓
LLM converts PDF → Markdown
     ↓
raw/sources/report.md
```

The latter can destroy tables, images, page relationships and provenance.

Normalization is therefore better understood as **source adaptation**, not “convert everything to Markdown.”

For example:

```text
PDF ──────────────────────► PDF
DOCX ─────────────────────► DOCX
EPUB ─────────────────────► EPUB

web page ──► cleaned HTML/MD + URL metadata
email ─────► MIME/text + sender/date/thread metadata
WhatsApp ──► structured MD/JSON
Telegram ──► structured MD/JSON
bookmark ──► URL + title + capture metadata
GitHub ────► repo/files + commit metadata
Google Doc ► exported document + source metadata
```

Hermes is especially well suited to coordinating this because normalization varies by source. The actual converters should preferably be boring deterministic code/skills—e.g. HTML extraction, Drive export, MIME parsing, Git commands—rather than an LLM rewriting the source.

So I'd actually rename the box in your diagram from:

**`normalize`**

to:

**`capture + adapt`**

or perhaps:

**`ingestion adapter`**.

That avoids giving the impression that every source needs to be transformed.

The resulting architectural rule is very clean:

> **Hermes gets knowledge *to* LLM Wiki. LLM Wiki decides what that knowledge *does to* the Wiki.**

That is the responsibility boundary I'd use for our Second Brain. memcite

## One design choice I'd make now

I would **not implement this as one giant Hermes prompt**.

I'd make the Hermes side a small collection of reusable Skills/tools:

```text
second-brain/
├── SKILL.md
│
├── adapters/
│   ├── file/
│   ├── web/
│   ├── email/
│   ├── chat/
│   ├── gdrive/
│   ├── github/
│   └── bookmark/
│
├── provenance/
├── dedup/
└── sync/
```

`SKILL.md` contains the orchestration policy; deterministic tools perform fetching, hashing, exporting and conversion. The LLM is used where **judgment/routing** is useful, rather than for operations like computing hashes or converting every PDF.

That gives us a much more robust Second Brain than **“Hermes reads stuff and writes Markdown.”**

And it exposes what I think is the next important design problem: **the Source Envelope / manifest**. Before implementing connectors, we should define exactly what metadata follows every artifact—stable source ID, original URI, version, hash, capture time, source type, parent/child relationship, etc. That contract is what lets Drive, Gmail, GitHub, WhatsApp and local files all behave consistently toward LLM Wiki.

The most important architectural insight is that **Hermes appears on both sides of the knowledge compiler**.

### Before compilation: Hermes is the Librarian's assistant

```text
Compiled Second Brain

        ↓
reason / research / act
```

LLM Wiki's current MCP/API is unusually useful here: an external agent can search the Wiki, read files, inspect the graph, retrieve unresolved review items, invoke Wiki chat and trigger source rescans. citeturn0search2turn0search3 Hermes itself now supports external MCP servers, so this is a natural integration boundary. citeturn0search6

## And Obsidian is deliberately *not* in the main processing path

This is another change from our earlier:

> `LLM Wiki → Markdown → Obsidian → MCP → Hermes`

That's misleading.

The proper relationship is:

```text
                       COMPILED WIKI
                       Markdown files
                             │
                    ┌────────┴────────┐
                    │                 │
                    ▼                 ▼
                Obsidian             MCP
                    │                 │
                    ▼                 ▼
                  HUMAN             Hermes
```

**Obsidian = human interface.**

**MCP = agent interface.**

Neither owns the knowledge.

The Markdown Wiki does. This matches LLM Wiki's design, which explicitly maintains Markdown/wiki-link output compatible with Obsidian. citeturn0search1

## The feedback loop is the part that makes this a Second Brain

The most interesting part isn't:

```text
documents → wiki
```

It's:

```text
                         WORLD
                           │
                           ▼
                        Hermes
                           │
                           ▼
                    RAW EVIDENCE
                           │
                           ▼
                      LLM WIKI
                           │
                           ▼
                  COMPILED KNOWLEDGE
                           │
                           ▼
                        Hermes
                           │
             ┌─────────────┼──────────────┐
             │             │              │
          answer         action      discover gap
                                           │
                                           ▼
                                      research /
                                    acquire evidence
                                           │
                                           ▼
                                      RAW EVIDENCE
                                           │
                                           └──► ...
```

For example, Hermes asks the Wiki:

> *What claims in my career profile don't have strong primary-source support?*

LLM Wiki exposes the knowledge and provenance. Hermes identifies gaps, finds or asks you for evidence, puts the resulting evidence back into the raw corpus, and LLM Wiki recompiles the affected knowledge.

That's the closed loop we've been trying to achieve.

### So I'd now summarize our architecture in one sentence:

> **Google Drive and other systems hold the world of evidence → Hermes acquires and orchestrates it → LLM Wiki compiles it into durable Markdown knowledge → Obsidian exposes that knowledge to you → MCP exposes it back to Hermes → Hermes reasons and acts from it, generating new evidence that feeds the compiler again.**

And importantly, this keeps **NotebookLM and Notion out of the core architecture**. They can be useful tools or source systems later, but neither is necessary for this Second Brain's fundamental loop. memcite

## Grok Bot is almost the inverse

Bots can coordinate with other Bots, pass work between themselves, learn workflows from demonstration and run those workflows on schedules. citeturn2search7

For something intended to become your personal knowledge infrastructure for perhaps decades, that's an important distinction.

```text
                       YOU

                       │
```

## 2. The DSH plugin ecosystem has exploded

This deserves some caution because DSH is extremely new.

The official project still describes itself as a **developer preview** and explicitly warns that compatibility-breaking changes will occur. citeturn0search0

But the surrounding plugin ecosystem has grown extraordinarily quickly. Third-party directories currently track thousands of DSH plugins; one current index lists **2,961 English-visible plugins**, with 1,565 having a verified install command as of October 1. citeturn0search6

I wouldn't equate:

> 3,000 plugins = 3,000 production-quality plugins.

But it does materially change DSH's viability.

# 3. Pi is philosophically different

Pi is intentionally tiny.

Its own description is essentially:

> **minimal terminal coding harness; adapt Pi to your workflow rather than adapting your workflow to Pi.**

It deliberately doesn't ship things such as subagents and plan mode as heavyweight built-ins. Instead, TypeScript extensions can add/replace tools, commands, model providers, UI, sandboxing, SSH, MCP, subagents, etc. citeturn0search9

So:

```text
Hermes/OpenClaw
      =
personal agent product
      +
extension system


Pi
      =
tiny agent kernel
      +
YOU construct the product
```

That distinction matters.

For your Second Brain, vanilla Pi isn't really:

```text
install
  ↓
connect Drive
  ↓
connect Telegram
  ↓
done
```

It's closer to:

```text
                   PI CORE
                      │
        ┌─────────────┼─────────────┐
        ▼             ▼             ▼
    extensions      skills        packages
        │             │             │
        ├─ MCP        ├─ brain      ├─ agents
        ├─ Drive      ├─ ingest     ├─ workflows
        ├─ Telegram   └─ audit      └─ memory
        │
        ▼
   YOUR PERSONAL
    AGENT HARNESS
```

Pi packages can bundle **extensions + skills + prompt templates + themes**, installed from npm, GitHub or local paths. citeturn0search8

There are already packages such as **Pi Agent Suite** adding agents, workflows, dynamic context compression, independent verification and MCP support. citeturn0search10

So Pi absolutely *can* become our harness.

It just requires more assembly.

# 4. But something very interesting has happened: Pi and DSH are converging

This is the biggest thing I'd pay attention to.

There is now a `pi2dsh` compatibility layer explicitly intended to:

> run unmodified Pi extensions as DSH plugins.

It handles Pi extensions, MCP configuration, subagents, memory and background tasks, with an explicit Pi-to-DSH compatibility layer. citeturn0search7

There's also broader DSH plugin-bridge work that imports:

```text
Pi packages
Claude Code plugins
Codex plugins
Agent Plugins
```

into DSH, including skills, MCP servers, hooks, commands and Pi extension lifecycle. citeturn0search11

That produces a rather fascinating hierarchy:

```text
                     DSH
              "everything plugin"
                       │
       ┌───────────────┼────────────────┐
       │               │                │
   native DSH        Pi ecosystem   Claude/Codex
    plugins          extensions       plugins
       │               │                │
       └───────────────┼────────────────┘
                       ▼
               PERSONAL HARNESS
                       │
                       ▼
                   LLM WIKI
```

If this compatibility layer proves robust, **DSH could become the superset harness**.

# 5. So why isn't DSH an automatic winner?

One phrase in its README prevents me from saying that:

> **Developer preview.**

And:

> **There will be compatibility-breaking changes.** citeturn0search0

For a toy agent, that's fine.

For a Second Brain that we want to run for **years**, it's significant.

Contrast:

```text
              DSH                         OpenClaw/Hermes

      more composable                     more opinionated
            ↑                                   ↑
      plugin everything                  personal-agent ready
            ↑                                   ↑
      huge flexibility                    less assembly
            ↑                                   ↑
      VERY new                            more established
```

So I distinguish **architectural attractiveness** from **operational readiness**.

# 6. Pi has a different long-term advantage

Pi's minimalism is actually attractive if you eventually want to *own* the Second Brain harness.

Instead of depending on:

```text
Hermes product architecture
```

we could build:

```text
              JAMES' HARNESS
                    │
                  Pi SDK
                    │
        ┌───────────┼───────────┐
        │           │           │
     ingestion     MCP       actions
        │           │           │

```

Pi explicitly supports **interactive, JSON, RPC and SDK modes**, including embedding Pi inside another application. citeturn0search9

That's substantially more interesting to me than merely replacing Hermes with another chatbot.

It turns Pi into an **agent runtime library**.

I would now design the Second Brain to support **three interchangeable harness targets from day one**:

```text
                         YOU

            ║   DeepSeek Harness     ║
            ║                         ║
            ║   [Pi-based custom]    ║
            ╚═══════════╤═════════════╝
                        │
                        │ common contract
                        ▼
                  RAW SOURCES
                        │
                        ▼
                   LLM WIKI
                        │
                        ▼
                  MARKDOWN WIKI
                        │
                       MCP
                        │
                        ▼
            ╔═════════════════════════╗
            ║ PERSONAL AGENT HARNESS  ║
            ╚═══════════╤═════════════╝
                        │

```

And I'd keep **all Second-Brain-specific intelligence outside the harness** wherever practical:

```text
Portable:

✓ raw-source contract
✓ source manifest
✓ LLM Wiki
✓ Markdown
✓ MCP interface
✓ SKILL.md instructions
✓ ingestion semantics
✓ provenance rules
✓ audit workflow


Harness-specific:

✗ authentication/connectors
✗ scheduler implementation
✗ UI/chat channel
✗ tool registration glue
```

That means switching:

**Hermes → OpenClaw → DSH → Pi**

should eventually be an adapter change rather than rebuilding your Second Brain.

### If we were choosing today

I'd narrow serious experimentation to **OpenClaw, DSH and Hermes**, while treating **Pi as the underlying DIY/runtime option rather than the default finished personal-agent product**.

DSH is the one whose trajectory I would watch most carefully. Its native MCP support, unified skill registry, “everything is a plugin” architecture, rapidly expanding plugin ecosystem, and now even **ability to consume Pi's ecosystem** make it unusually well aligned with the portable Second Brain architecture we've arrived at. But until its developer-preview/compatibility-breaking phase settles down, I would not make the durable parts of the Second Brain dependent on DSH-specific APIs. citeturn0search0turn0search1turn0search2

In other words: **LLM Wiki should remain the brain; DSH/Hermes/OpenClaw/Pi should remain replaceable nervous systems.** memcite

## 2. Is the Hermes skill dependent on `hermes_LLMwiki_Obsidian`?

**No—not as a software dependency.**

# 5. There's an additional limitation in Nashsu's *skill* we should recognize

- page reading;

Hermes adds evidence to the raw corpus; Nashsu owns compilation.

The easiest way to understand **“Wiki compiler”** is:

> **The component that reads raw source material and turns it into the organized, maintained Wiki.**

“Compiler” is our architectural term, borrowed from software compilers; it isn't the official name of a Nashsu component.

### 1. What exactly does the Wiki compiler do?

Imagine you add:

```text
raw/sources/
└── new-paper-about-agents.pdf
```

The **Wiki compiler** does roughly this:

```text
new-paper.pdf
      │
      ▼
┌─────────────────────┐
│    WIKI COMPILER    │
│                     │
│ Read/understand     │
│        ↓            │
│ Find concepts       │
│        ↓            │
│ Compare with Wiki   │
│        ↓            │
│ Find contradictions │
│        ↓            │
│ Update pages        │
│        ↓            │
│ Create links        │
│        ↓            │
│ Record sources      │
└─────────┬───────────┘
          ▼

wiki/
├── concepts/
│   ├── multi-agent.md       ← updated
│   └── agent-memory.md      ← created
├── entities/
│   └── some-framework.md    ← updated
└── overview.md              ← updated
```

Nashsu actually implements this as a two-stage ingest: **analysis first, generation second**, including finding connections/contradictions with existing knowledge and then generating/updating Wiki pages. citeturn0view0

# 5. This actually changes how I think we should design the Second Brain

Earlier, we were giving Hermes quite a lot of responsibility:

```text

├── ingestion
├── normalization
├── knowledge compilation
├── knowledge maintenance
├── auditing
├── research
└── actions
```

With current Nashsu, that's unnecessary.

I'd simplify it to:

```text
             SECOND BRAIN

          ┌─────────────────┐
          │ SOURCE SYSTEMS  │
          └────────┬────────┘
                   │
                   ▼
             🤖 HARNESS
               Hermes
                   │
              acquisition
                   │
                   ▼

        ╚══════════╤═════════╝
                   │

            COMPILED BRAIN
                   │
             ┌─────┴─────┐
             ▼           ▼
          Obsidian      MCP/API
          [human]          │
                           ▼
                       🤖 HARNESS
                         Hermes
                           │
                    reason / research
                       automate / act
```

And this gives us a very useful architectural property:

### Hermes becomes genuinely replaceable.

```text
                    AGENT HARNESS
                         │
           ┌─────────────┼──────────────┐
           ▼             ▼              ▼

               ╚══════════════════╝
```

That's much healthier than having your accumulated Second Brain depend on Hermes.

One additional current Nashsu feature reinforces this separation: its API is localhost-only and token-protected, specifically allowing external agents/tools to query the Wiki while the application remains its own independent service. citeturn0search1turn0search7

> **Nashsu = the brain builder/maintainer.**  
> **Obsidian = the window through which you inspect the brain.**  
> **Hermes = the hands, feet and personal assistant that brings information in and uses the brain to do things.**

That is a cleaner architecture than our initial Hermes-heavy version—and it makes the earlier investigation into **Hermes vs OpenClaw vs DSH vs Pi** much less consequential to the durability of your Second Brain. memcite

Yes—there are performance costs to the **Harness → Nashsu → LLM → Wiki → MCP → Harness** separation, but I don't consider them serious enough to abandon the architecture.

| Performance downside | Impact | Why |
|---|:---:|---|
| 🐢 **Extra hops** | 🟡 Low | Harness → Nashsu API/MCP adds latency versus one agent doing everything |
| 🤖 **More LLM calls** | 🟠 Medium | Nashsu's compilation can involve analysis + generation/reconciliation calls |
| 💰 **Higher token cost** | 🟠 Medium | New sources may require comparing against existing Wiki knowledge |
| 📚 **Large-corpus compilation** | 🟠 Medium→High | As thousands of sources/pages accumulate, retrieval, graph maintenance and affected-page analysis become heavier |
| 🔄 **Duplicate reasoning** | 🟡 Medium | Nashsu may understand something during compilation, then Hermes later reasons over the compiled result again |
| ⏳ **Eventual consistency** | 🟡 | A newly captured source isn't necessarily immediately reflected in the compiled Wiki |
| 🧩 **Two processes/state systems** | 🟡 | More IPC, queues, indexing and failure points than an all-in-one Hermes solution |
| 🔍 **Information compression** | 🟠 Important | Hermes querying only the compiled Wiki may lose nuances present in the original source unless it can drill back to evidence |

The **biggest practical cost isn't MCP latency**. It's this:

```text
raw document
     ↓
Nashsu LLM analysis       ← $$$ + time
     ↓
knowledge compilation
     ↓
Wiki
     ↓
Hermes retrieves Wiki
     ↓
Hermes LLM reasoning      ← $$$ + time again
```

So we're deliberately trading some **latency + token cost** for much better:

```text
persistence
maintainability
provenance
specialization
harness independence
```

### One optimization I'd consider essential

Don't make Hermes *always* reason only from the compiled Wiki:

```text
             COMPILED WIKI
                  │
             search / graph
                  ▼
               Hermes
                  │
        need deeper evidence?
             YES  │
                  ▼
            RAW SOURCES
```

That gives you **fast Wiki-first retrieval** for most questions while preserving access to primary evidence for difficult ones.

**Bottom line:** 🟢 Good architectural trade-off. The meaningful downside is **LLM computation/token duplication**, not the extra software/API layer. At personal Second-Brain scale, I'd strongly favor the separation.
