Five ways to fuse keyword and embedding search

We changed one search setting at a time and scored the same questions on accuracy, recall, time, and chat-model calls. The manual hybrid is best when each file can contribute at most five chunks. Splitting the question raises bundled-answer accuracy and spends an extra chat call. It does not find the labeled ticket more often.

Numbers are medians and pass counts from section 8 of the bundled manual-and-ticket analysis. RRF (reciprocal rank fusion) is the step that turns a keyword ranking and an embedding ranking into one list: each list adds 1 / (60 + rank).

Ticket search already had a third signal

Before those five profiles, past-ticket search was compared three ways on the same 100 questions over 1,000 closed tickets. The question each time was whether the right old ticket came back first. Two of the ways are the usual pair: an embedding list (similar meaning) and a BM25 list (shared words, including the odd fault code). The third is a small specialized bump on top of fusing those two lists.

Mode What is combined Right ticket first When the question contains a fault code (20)
A · embeddings only One meaning list. No keyword list. 0.25 0.15
B · embeddings + BM25 Fuse the two rankings by position. The raw scores are not added. 0.44 0.15
C · B, plus a code bump After the fuse, add weight when the question’s FRU-E### code is on that ticket. 0.54 0.65

Fusing keywords with embeddings is what moved everyday wording (0.25 to 0.44). It did nothing for the fault-code questions: those stayed at 0.15. The code bump is what moved them, from 0.15 to 0.65, and that is the whole of the step from 0.44 to 0.54. Paraphrases and mixed-wording questions did not change between B and C. So the bump is not a smarter embedding. It is a third signal for an identifier the two general lists treat like any other token.

Every profile below holds ticket search on mode C. The profiles change the manual index and, in the last step, how the question is split.

What each profile changed

The ticket index and ticket mode C stayed put through the first four profiles. Only the manual leg, and then the way a question is split, moved.

1 · PRE-T0 Filter the model after a 200-row pool. Keyword score is in-process word overlap. Chunks are fixed 2,000-character windows. Baseline
2 · T0 Filter brand and model inside the database. Keyword leg becomes Tantivy BM25. Chunks stay fixed windows. Faster search, weaker answers
3 · D2 page Re-chunk manuals on headings, 592 chunks. No cap on how many chunks one file may send into the fuse. Judge returns to baseline
4 · Pack page Same chunks. Before the fuse, keep at most five chunks from each manual file. Best manual-fact recall
5 · D7 v3 Same manual fuse. Split the customer question. One chat call reorders the ticket list, then two tickets go to the answer. Original run, questions unchanged

Step 5 is b20-evo18-d7-v3-20261028. Later runs rewrote gold ticket labels or three questions. Those are outside this comparison.

Six rows in that original D7 v3 run still pointed at open tickets rather than the resolved ticket. The 16 of 20 judge score is the published number for this profile. It is not a clean comparison against the earlier 14 of 20, because those six labels differ.

Accuracy of the bundled answer

Accuracy here is the judge: did the written answer contain the required ticket resolution and the required manual fact. Twenty questions.

T0 made the keyword leg a real BM25 index and filtered the model in SQL. Manual search got faster. Bundled answers got worse, 11 of 20. Heading-sized chunks brought the judge back to 14. The question split then reached 16, with the label caveat above.

Recall

Two different recalls. The ticket recall is whether the labeled past ticket was one of the two tickets shown to the answer. The manual recall is how many of 60 manual-only questions could be answered from the retrieved chunks. A separate 100-question ticket probe, recall at rank 1, stayed at 0.54. It was not re-run after T0, because the ticket index did not change.

Heading chunks are what moved manual recall, from 33 of 60 to 42. Capping each file at five chunks added two more, to 44, without giving up the bundled judge. The ticket top-two rate did not move until D7 v3, and then it fell from 10 of 20 to 7 of 20. The chat reorder is a different picker. It is not a stronger ticket search.

Time

Time is the median milliseconds for one question. The chart is the manual search only. Answer writing and judging stay in a band of about 1.1 to 1.8 seconds on every profile, so they do not decide the comparison.

What to keep

Use pack page for the manual hybrid: heading chunks, Tantivy keyword leg, database model filter, and at most five chunks from each file before RRF. That is the best manual-fact recall in this set, the bundled judge is back to the baseline 14 of 20, and manual time stays near 330 milliseconds.

  • Ticket hybrid. Leave it on the same ranked-list fuse used from PRE-T0 through pack page. Labeled-ticket recall did not improve when the manual leg changed, and the D7 v3 chat reorder made it worse, 7 of 20.
  • Question split. D7 v3 is the highest bundled judge here, 16 of 20, at about twice the manual time and one extra chat call per question. Treat that gain as provisional until the six open ticket labels are aligned with the earlier runs.
  • Do not ship T0 alone. It is the fastest manual leg and the worst bundled judge.

Deferred: reorder a deeper manual list

A later probe, on one hard question, retrieved 20 fused chunks per clause and asked a chat model to reorder them, then kept two chunks from each clause. That passed when the right manual paragraph was already rank 12. The same depth did not contain the missing paragraph for the other two failures in the full suite. Running it on all 20 questions would add two chat calls and several seconds per question. That profile is not in the decision above.
